# AppleSAP

A Swift package containing `AppleSAPKit` and the ArgumentParser executable `AppleSAPTool`. The same targets are also exposed by the parent ApplePackage package, so clients can depend on the `AppleSAPKit` product without a nested local-package dependency.

The kit implements the recovered F_875304 signature construction directly. Session initialization, the 128-bit E transform, and F2 run in Swift; the small `CSAPRandom` target implements the recovered RNG/F1 byte algorithm in C. SHA-1 and SHA-256 use [Lakr233/openssl-spm](https://github.com/Lakr233/openssl-spm). There is no Python runtime, IR interpreter, instruction dispatcher, original executable, or original image dependency.

## Library

```swift
import AppleSAPKit
import Foundation

let snapshot = try Data(contentsOf: snapshotURL)
let signer = try SAPSigner(snapshot: snapshot)
let signature = try await signer.sign(requestBody)
let headerValue = signature.base64EncodedString()
```

Keep one signer for a session: its actor serializes signing and advances the RNG for each call. It generates F1 once and reuses the cached blob. Concurrent callers should associate each returned signature with the exact body supplied to that call.

`SAPSession` is a Codable value containing the logical source bytes, F2 inputs/tail, F3, RNG state/seeds, and virtual address salts. Use `SAPSigner(session:)` when these inputs are already available. The original snapshot decoder accepts an **unused complete `post_handshake` state before the first signature**; later snapshots and already-cached F1 states are rejected. Addresses describe the original virtual layout and are never host pointers.

This package does **not** generate a fresh SAP handshake. A saved session is signing material, not Apple account credentials; keep it private. No recorded sessions or credentials are distributed in this repository.

## CLI

From this directory:

```sh
swift run AppleSAPTool sign --context /private/session.json --hex 616263 --hex 616263
swift run AppleSAPTool sign --context /private/session.json --body-file request.plist --format base64
swift run AppleSAPTool export-session --context /private/session.json --output /private/logical-session.json
swift run AppleSAPTool sign --session /private/logical-session.json --hex 616263
```

Repeated bodies are signed consecutively. Hex bodies are processed first, then file bodies, each in supplied order. An empty `--hex ''` signs an empty message. Output defaults to JSON lines with the full signature, IV, tag, and call index; `--format hex` and `--format base64` are available. `--iv-address` accepts decimal or `0x` notation for original snapshots; logical sessions retain their stored address. `--platform` defaults to 1.

The parent repository also supports `swift run AppleSAPTool …` and `swift run ApplePackageTool login … --sap-context /private/session.json`. The latter signs the final plist body and sends `X-Apple-ActionSignature`; retries, redirects, and interactive 2FA reuse the same actor.

## Algorithm

```text
blob = 03 || BE32(platform) || BE32(256) || F1
          || BE32(len(F2)) || F2 || BE32(159) || F3 || zero padding to 16 bytes
d = SHA1(blob || body)
a = E(IV XOR d[0:16])
tag = E(a XOR (d[16:20] || 12 zero bytes))
signature = 02 || IV || tag || BE32(len(blob)) || blob
```

E derives its parameters from 576 source bytes. It expands to a 17-byte state, runs nine word mixes interleaved with eight nonlinear byte-table rounds, and decodes back to 16 bytes. The recovered components include encoded AES inverse S-box and inverse MixColumns operations. Equivalence to one standard AES-128 key schedule/call has not been established; the explicit algorithm defines the result.

The 144,324 bundled table bytes are fixed algorithm data. `Resources/manifest.json` records each length/hash and the source image hash; the loader verifies SHA-256 with OpenSSL. The source image supplied 200 byte tables, 72 word tables, and four carry-mask arrays. F2 uses fixed byte substitutions, four shared word T-tables, and final byte-linear maps. There are no session-specific parameter caches or expected signatures in production resources.

## Verification

```sh
swift test
# Optional, against the private research corpus (never copied into this repo):
SAP_CORPUS_ROOT=/path/to/ipatool_sap swift test --filter SAPCorpusTests
```

Public tests use an entirely synthetic, never server-issued session. They check complete consecutive signature hashes independently generated by the direct reference, F2/E blocks, changed-body behavior, serialization, static-resource hashes, and input validation. The optional private-corpus test compares eight sessions × 128 consecutive complete signatures and 128 additional fresh-state messages. The release CLI separately passed the same **1024 + 128** complete-signature comparisons, including messages up to 65,536 bytes, plus malformed Unicode/hex input and logical-session export/import checks.

These are finite cross-implementation checks, not a whole-input-space formal proof or evidence of a successful Apple account login. ApplePackage's offline request tests separately verify the exact body/header connection without credentials or network access. Its opt-in live probe uses only fabricated credentials and reports server responses separately from signature acceptance.

When distributing a built executable, keep its generated `AppleSAP_AppleSAPKit.bundle` (standalone build) or `ApplePackage_AppleSAPKit.bundle` (parent build) beside the binary. OpenSSL is linked statically; no original native signing library is loaded.
